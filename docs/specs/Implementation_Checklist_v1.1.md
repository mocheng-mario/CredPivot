# CredPivot 首发实施清单（最终版）
依据 Plans/CredPivot_V1.1_Design.md 当前版本。编号可直接引用，例如 "M1-3"。清单只表示依赖顺序，不是工期。

## 总原则

- M1 的加密格式通过验证前，所有开发只用假数据。
- 每个阶段完成后按"完成标准"自检，通过才进入下一阶段。
- Touch ID 首版按方案 A 做（LAContext 门槛加登录 Keychain），方案 B 留到有开发者账号后迭代。

# M0 平台可行性（假数据）
| # | 事项 |
| :--- | :--- |
| M0-1 | 搭建 Mac App 骨架：Flutter + Swift 平台层，开启 Hardened Runtime，用本地证书签名（开发期可用 `xattr` 去除 quarantine 标记） |
| M0-2 | 用 `SMAppService` 实现登录常驻和菜单栏图标，关闭主窗口不退出进程 |
| M0-3 | 在 App 进程内跑一个最小 Rust Agent，Flutter 通过 FFI 调用，并加文件锁保证单写入者 |
| M0-4 | 实现 Touch ID 方案 A：`LAContext` 门槛 + 登录 Keychain 包装；顺带记录方案 B 的可行性结论 |
| M0-5 | 实现 Native Host 中继：校验父进程是 Chrome，App 侧校验 socket 对端的 Team ID，Host 连不上 App 时能拉起 App |
| M0-6 | 做 Chrome MV3 扩展原型：Native 端口、service worker 被回收后请求作废、按 `frameId` 和 `documentId` 投递秘密 |
| M0-7 | 做 SSH Agent socket 原型：短路径（≤104 字节）、`IdentityAgent` 一键接入、Ed25519 签名 |
| M0-8 | 验证空闲、锁屏、睡眠三种锁定，并测量窗口关闭后 Flutter 的内存占用 |
| M0-9 | 汇总结论，回写文档的平台相关条款 |

完成标准：在最低支持的 macOS 上真机跑通：Chrome 保存和填充、终端 SSH 签名；关窗口后仍可服务；锁定和取消能让等待中的请求失效。

# M1 格式与恢复
| # | 事项 |
| :--- | :--- |
| M1-1 | 写 `CPVC1` 控制配置规范：槽结构、配置 MAC、版本 |
| M1-2 | 写 OVB1 字节规范：头部字段、AAD 编码、HKDF 输入输出 |
| M1-3 | 在 Rust Core 实现 Argon2id、HKDF、AES-GCM、HMAC，以及恢复密钥（Base32 加校验码） |
| M1-4 | 实现密钥槽：创建、主密码解锁、恢复密钥解锁、改主密码（原子替换加崩溃恢复） |
| M1-5 | 配置 SQLCipher：固定版本、原始密钥模式，并审计 WAL 和临时文件 |
| M1-6 | 实现 OVB 归档的写出与读取，带文件大小、KDF 参数、嵌套深度的上限 |
| M1-7 | 实现"目标目录流水线"：生成副本 → 校验 → 显式切换，供迁移、重建、恢复共用 |
| M1-8 | 实现 `credpivot-cli`：`inspect`、`verify`、`recover`、完整逻辑导出，口令只走交互输入 |
| M1-9 | 发布测试向量，并用不复用 Core 的独立解析路径验证 |
完成标准：主密码和恢复密钥各自能在空目录恢复；独立解析验证通过；改密在每个崩溃点都可恢复；超限输入被拒绝。

# 风险项（排期时关注）
- M0-4 和 M0-5：Keychain 行为和 Host 的进程校验最容易出意外，建议最先做。
- M1-2：字节规范是整个项目风险最高的一项，通过前不要保存真实秘密。
- M4-3：Chrome 商店审核周期不可控，M2 完成后就可以提前提交测试版。
- 常驻内存：Flutter 常驻的内存占用若不可接受，按设计在 M0-8 评估窗口关闭时释放视图。
