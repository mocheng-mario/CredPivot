## 总体评价

Core / Agent / 平台层 / 扩展的边界方向合理，SQL 参数化、关键业务事务、修订冲突检查、密钥派生域分离、空目标目录恢复等基础值得保留。

但当前成熟度仍是原型。主要问题是安全属性没有贯穿全链路：声明锁定不等于所有入口停止服务；填充授权记录了上下文不等于最终按该上下文投递；重建成功不等于旧泄露材料失效；写入临时文件不等于跨文件崩溃一致性。继续扩展菜单和凭据类型的收益，低于先修复这些问题。

P1 表示应优先修复的安全、数据可靠性或关键功能缺陷；P2 表示常规优先级的功能和一致性问题。

## 1. [P1] IPC 对端校验可以被同名可执行文件通过

位置：`crates/agent/src/peer_auth.rs:29-39`；`crates/native-host/src/chrome_parent.rs:15-24`；`crates/agent/src/ipc.rs:37-40,273-285`。

Agent 只要看到进程可执行文件名等于 `credpivot-native-host` 就放行。后面的 App 路径分支没有收紧条件，前面的同名分支已返回成功。Host 自身也只比较 Chrome 文件名，没有实现注释声称的签名校验。

触发条件：同一 macOS 用户下的另一个进程采用该文件名并连接 socket。0700 目录可以限制其他用户，但不能隔离同用户进程。Vault 已解锁时，该进程能直接发送 `CredentialList`、`CredentialGet` 等完整 Agent 请求，而不受 Native Host 的动作映射限制。

最小修复：按设计校验连接对端的代码身份及可信签名要求，并区分进程内管理入口与外部 Host 可调用的请求集。开发绕过不能成为发行构建的默认可用路径。不要把增加文件名或路径字符串条件当成身份认证。

## 2. [P1] 空闲锁定只作用于外部 IPC，App 和 SSH 可以绕过

位置：`crates/agent/src/ipc.rs:54-70`；`crates/agent/src/client.rs:26-31`；`crates/agent/src/ssh_agent.rs:42-58`；`crates/agent/src/runtime.rs:51-61`。

`idle_expired()` 只在 Unix IPC 接收函数中执行。App 的 FFI 直接调用 `call_in_process -> handle_request`，SSH 也只检查 `unlocked`，没有检查超时。后台计时器只负责恢复点，没有负责锁定。

因此，主密码解锁后超过空闲时间，只要没有其他 IPC 请求先触发锁定，App 仍可读取秘密，SSH 仍可签名。SSH 请求还会先更新活动时间，使已经过期的会话继续存活。

最小修复：所有入口在读取秘密或刷新活动时间前执行统一的会话有效性检查；需要空闲后及时清除内存密钥时，增加独立锁定计时。锁定同时清理待处理填充授权。

## 3. [P1] 菜单栏或系统触发锁定后，UI 仍可展示缓存的恢复码

位置：`apps/macos/macos/Runner/AppDelegate.swift:38-40`；`apps/macos/macos/Runner/LifecycleBridge.swift:42-46`；`apps/macos/lib/main.dart:42-47,85-97`；`apps/macos/lib/credentials_page.dart:594-601,689-710,742-753`。

平台锁定只调用 Rust，没有通知 Flutter 更新 `_status`。安全中心预先把全部恢复码装入 `_recoveryCodes`；打开恢复码弹窗只读取该缓存，不向 Agent 查询或重新验证。

触发步骤：解锁并加载安全中心 → 点击菜单栏“锁定 Vault” → 继续点击恢复码。此时 Rust 已锁定，但 Flutter 的 `unlocked` 仍可为 true，缓存内容仍能被展示和复制。已经打开的秘密弹窗也没有锁定联动关闭逻辑。

最小修复：发送会话状态变更事件，收到锁定时清空秘密缓存、控制器并关闭秘密弹窗；恢复码列表只加载摘要，查看时按 ID 获取。主密码控制器同样不应在锁定后继续保留内容。

## 4. [P1] Agent 重启没有停止旧服务任务

位置：`crates/agent/src/runtime.rs:38-65,75-77`；`crates/credpivot-ffi/src/lib.rs:54-64`。

`shutdown()` 只 abort 包含 `join!` 的外层任务。IPC、SSH、恢复点任务都是单独 `spawn` 的任务；丢弃它们的 JoinHandle 不会取消任务。Tokio 文档明确说明该行为：[JoinHandle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)。

FFI 重启保留同一 Runtime，所以旧任务继续持有旧 Vault、数据库连接和可能仍存在的 VMK，单写入锁却已经释放，随后又启动新 Agent。已经接收的连接也被单独 spawn，未纳入关闭管理。可能出现后台重复任务、旧会话残留、两个状态持有同一工作库等问题。

最小修复：直接持有并取消、等待实际服务任务；关闭过程先锁定会话和作废授权，再停止连接任务，确认退出后释放单写入锁及重建 socket。无需为此增加新的服务框架。

## 5. [P1] 安全重建先改原库，失败窗口会导致配置与数据库密钥不一致

位置：`crates/core/src/vault_pipeline.rs:168-200`；`crates/agent/src/vault_session.rs:476-493`。

流程先原地 `rekey_database`，再生成新槽并写 `vault.json`。数据库 rekey 成功后，若进程退出、新槽生成失败或配置写入失败，磁盘数据库需要新 VMK，但现有配置只包装旧 VMK；新 VMK 没有可靠落盘。

Agent 调用前创建恢复点，能缓解数据丢失，但不使原工作库具备崩溃原子性；Core API 自身也不强制创建恢复点。当前不能满足设计文档 12.7 的“任何环节失败保持原路径可用”。

最小修复：按既有设计在新的空目录生成并校验完整新库，最后切换工作路径，失败保留源库。不要仅调整两个写入的先后顺序，跨文件一致性问题不会因此消失。

## 6. [P1] 安全重建复用旧恢复密钥，无法处理恢复密钥泄露

位置：`crates/core/src/vault_pipeline.rs:177-180,187-198`；设计：`docs/Plans/CredPivot_V1.1_Design.md:584-587,649`。

输入的旧恢复密钥用于认证后，又作为 `create_recovery` 的秘密包装新 VMK；Vault ID 也保持不变。知道旧恢复密钥的人，如果取得重建后的新配置和新库，仍能解密。

这与设计明确要求的新 Vault ID、新 VMK、新恢复密钥不同。这里不是要求撤销旧备份；问题是旧恢复密钥对新库仍然有效。

最小修复：认证使用旧恢复密钥，重建输出使用全新恢复密钥，交给用户保存并确认后切换。与上一项在同一修复中完成。

## 7. [P1] Chrome 填充授权没有绑定最终接收秘密的网页文档

位置：`apps/chrome-extension/popup.js:35-67`；`apps/chrome-extension/background.js:100-121`；`crates/agent/src/ipc.rs:213-264`；`apps/chrome-extension/content.js:1-7`。

prepare 和 consume 都由 popup 发出，background 却把消息发送者的 tab/frame/document 当成目标网页上下文。popup 自身不是目标网页，尤其 `tab_id` 会落到 0。最后投递只使用先前取得的 tab ID 和 `frameId: 0`，没有指定原目标 documentId。

若目标标签在 suggest 与最终投递之间发生导航，秘密可能被送到同一标签的新文档。content script 也不检查目标 origin。Agent 虽记录 origin/tab_id，却没有在 consume 中校验二者，也没有校验凭据 origin 与授权 origin 一致。

最小修复：从真实目标 frame 建立请求，绑定 tab/frame/document/origin；Agent 校验凭据归属；最终投递指定已授权 documentId；导航或端口断开时作废授权，context 不完整则拒绝。不能只在发送前再比较一次 URL，之后仍可能导航。

## 8. [P1] SSH 协议与导出的公钥格式存在确定性错误

位置：`crates/agent/src/ssh_agent.rs:10,28-64,91-117`；`crates/core/src/repo_m2.rs:273-278,448-453`；`crates/agent/src/vault_session.rs:272-277`。

1. 请求类型 11 的 identities 响应应为 12，当前写成 2。2 是旧 RSA identities 响应，标准客户端不会把它当作 SSH2 身份列表。依据：[OpenSSH authfd.h](https://raw.githubusercontent.com/openssh/openssh-portable/master/authfd.h)。
2. 展示和保存的 OpenSSH 公钥只 Base64 编码 32 字节原始公钥，缺少算法名及 SSH string 长度编码。Agent 内 `ed25519_key_blob` 已按结构编码，但展示路径没有使用。依据：[RFC 8709 第 4 节](https://www.rfc-editor.org/rfc/rfc8709.html#section-4)。
3. 每个连接只处理一个报文即结束，不能支持同连接上的后续请求；签名时跳过 key blob，不核对客户端请求的身份。

最小修复：修正消息常量、统一公钥 blob 编码、连接内循环处理报文，并校验请求密钥。不要把单独调用 Ed25519 sign 成功当成 SSH 客户端兼容性成立。

## 9. [P1] 某些合法主密码能创建 Vault，却无法通过 UI 再解锁

位置：`apps/macos/macos/Runner/CredPivotPlatform.swift:43-51`；`apps/macos/lib/agent_bridge.dart:8-9,79-89`。

创建 Vault 使用 Dart `jsonEncode`；解锁使用 Swift 字符串拼 JSON，只转义双引号，没有处理反斜杠和控制字符。

例如用户密码含字面量反斜杠加 n：创建时存储的是该字面量，解锁 JSON 解码后却变成换行。其他反斜杠组合可能直接成为非法 JSON；UI 将错误统一展示为密码不正确。

最小修复：主密码解锁复用现有 `AgentBridge.request`，或在 Swift 使用 JSONSerialization。秘密和其他用户输入均不应手写 JSON 转义。

## 10. [P2] TOTP URI 入库会静默丢失算法、位数和周期

位置：`crates/core/src/totp.rs:12-22,53-67`；`crates/core/src/repo_m2.rs:463-487,654-661`；`crates/core/src/vault_db.rs:165-167`。

URI 解析后只存 `get_secret_base32()`，读取生成验证码时重新使用固定 SHA1、6 位、30 秒。因此一个合法 SHA256/8 位/60 秒 URI，保存后按另一套参数计算，无法保留原来的验证码语义。直接调用 `totp_code_now(uri)` 的测试无法覆盖真实的入库再读取路径。

最小修复：保存并使用算法、位数、周期；若当前只支持默认组合，则保存前明确拒绝非默认参数。不要默默降级。URI 解析失败后仅提取 secret 的回退也需要采用同样限制。

## 11. [P2] Native Messaging 并发请求会串响应，断连后等待不结束

位置：`apps/chrome-extension/background.js:30-38,43-61`；`crates/native-host/src/main.rs:60-79,172-191`。

JS 用顶层 request_id 匹配响应，但 Host 的成功和失败封装均没有回传该字段。判断逻辑在响应无 request_id 时直接接受，因此有两个并发请求时，第一个响应会同时 resolve 两个 Promise。Host 顺序处理消息不能解决客户端已同时挂上两个 listener 的问题。

断连时只删除 inflight 记录，没有 reject 对应 Promise，也没有超时，连接失败可表现为无限等待。

最小修复：Host 对所有响应回传原 request_id；JS 严格相等匹配，并在断连、超时统一结束对应 Promise。

## 12. [P2] Bitwarden 导入器不接受真实普通 JSON 导出的外层结构

位置：`crates/core/src/bitwarden_import.rs:33-34`；`apps/macos/lib/credentials_page.dart:607-612`；`crates/core/tests/m2_features.rs:35-46`。

GUI 把整个文件直接传入 Core，Core 却直接反序列化为 `Vec<BwItem>`。Bitwarden 普通 JSON 是包含 items 等字段的对象，不是裸数组。依据：[Bitwarden 官方格式](https://bitwarden.com/help/condition-bitwarden-import/#condition-a-json)。

现有测试自己构造了裸数组，仅证明这个内部输入格式可用。即便修复外层结构，当前代码还只取第一个 URI，未支持的 TOTP、备注、自定义字段等没有逐项损失报告；原始带路径 URI 写入 origin 后，也不能匹配浏览器仅传 origin 的严格相等查询。

最小修复：先适配真实的普通 JSON 外层对象，给出明确支持范围及字段跳过报告，避免声称完整迁入。暂不需要为此建设通用导入框架。

## 13. [P2] 安全中心恢复成功后，必然在切换工作库时失败

位置：`apps/macos/lib/credentials_page.dart:642-650,713-727,752-753`；`crates/agent/src/vault_session.rs:111-120`。

安全中心只有解锁时可用；恢复完成后直接调用 `vaultOpenDir`，但后端 `open_dir` 明确要求先锁定。恢复文件已落盘，UI 却接着显示错误，用户无法分辨是恢复失败还是切换失败。

最小修复：明确区分“恢复到新目录”和“切换当前库”；用户选择切换后先锁定、清理 UI 秘密状态，再打开目标目录并更新父页面状态。

## 14. [P2] 会话状态更新没有失败回滚，Touch ID 还会制造半解锁状态

位置：`crates/agent/src/vault_session.rs:177-208,216-229,459-493`；`apps/macos/macos/Runner/CredPivotPlatform.swift:175-182`；`apps/macos/lib/main.dart:235-239,390-395`。

主密码解锁先设置 vmk/unlocked，再执行可能失败的数据库挂载；改密和迁移在执行可能失败的操作前先清空 db。失败后会留下 unlocked=true、db=None 等组合。

Touch ID token 校验成功只设置 unlocked，不恢复 VMK/DB；UI 随后隐藏主密码解锁按钮，却提示用户再次点击该按钮。锁定没有清除 ssh_signing_key，因此这类半解锁还能重新放行内存中的 SSH 签名材料。App 重启后，Keychain 已有 token 的分支又不重新向 Agent 注册，而新会话的 token 为 None。

最小修复：保证“已解锁”意味着完整可用的会话；先构造成功所需材料再提交状态，失败保留原会话或完整锁定。Touch ID 设备包装未完成前，应独立表示操作门槛通过，不能等同于 Vault 解锁。锁定应释放签名私钥。

## 还需处理的可靠性风险

1. OVB 覆盖导出直接 `fs::write`（`crates/agent/src/vault_session.rs:233-241`、CLI `main.rs:131-135`）。若用户选择已有归档，文件会先被截断，磁盘满或写入中断可能破坏原备份。建议同目录临时文件写完、校验、同步后再替换；当前未做故障复现。
2. Argon2 只限制 memory_kib，没有业务层 iterations 上限（`crates/core/src/crypto.rs:22-32`）。来自配置/OVB 的参数在认证前使用，恶意高迭代输入可造成长时间计算；Swift 主线程同步调用 FFI 会放大卡顿。建议补齐 KDF 参数预算和大文件读取前的限制。
3. 迁移路径仅赋给内存字段 `vault_dir`（`crates/agent/src/vault_session.rs:469-472`）；新启动仍从环境变量或默认目录取路径（`crates/agent/src/paths.rs`）。默认启动情况下重启会回到原库。应持久化已验证的新路径指针，避免用户误以为迁移后写入丢失。
4. 默认 SSH 身份只在 attach_database 时同步；生成新默认密钥没有更新内存 signing key（`crates/agent/src/vault_session.rs:95-104,393-396`）。UI 默认标记与实际签名身份可不一致，应在修改默认身份成功后同步或按请求读取当前身份。

## 测试与验证评价

本次只读测试源码，未执行：

1. `crates/agent/tests/lock_policy.rs` 证明显式 Lock 的部分行为，没有覆盖空闲超时、FFI/SSH 多入口、菜单栏锁定或重启后的会话清理。
2. `crates/core/tests/m2_features.rs` 的 Bitwarden 测试使用裸数组，不能证明兼容官方导出。
3. TOTP 内嵌测试检查当前码长度和数字形状，没有在固定时间核对标准向量，也没有覆盖入库前后算法参数一致性。
4. `crates/core/tests/m3_fault.rs` 只有目标目录非空拒绝案例，没有磁盘满、rekey 与配置提交之间中断等故障验证。
5. `crates/core/tests/m3_restore.rs` 的安全重建测试只检查 VMK 变化和数据仍可读，没有验证旧恢复密钥对新库失效。
6. Swift 测试仍是空模板，Flutter 测试只检查壳层标题，覆盖不到主密码 JSON 编码和真实平台锁定链路。

建议后续只围绕以上问题增加针对性验证：真实 OpenSSH 协议交互、带特殊字符主密码往返、官方导出样例、非默认 TOTP 参数入库往返、跨入口锁定、重启清理、新目录重建的失败保源。无需默认跑全仓测试或为了覆盖率大量新增重复测试。

## 修复顺序与架构建议

1. 先处理可信入口、统一锁定、UI 秘密清理和 Runtime 退出，确保谁能读取秘密、何时失去权限是可靠的。
2. 再处理安全重建与备份替换，确保失败后原有数据仍然可用、旧恢复材料不能打开新库。
3. 随后修正 SSH、浏览器投递、密码编码、TOTP 和 Bitwarden 的真实外部契约。
4. 最后再整理交互、文件拆分和命名。现有 crate 分层可以保留，不建议引入事件总线、通用 Repository 接口或新的微服务。必要的会话状态通知不需要升级成通用事件架构。

可选维护改进：保留 CoreError 的类型化分类到 AgentResponse，避免使用错误文本 contains 判断 conflict；高耗时 KDF/备份不要阻塞主线程；生产路径中的 FakeCredential、M0 名称在真实行为稳定后再局部清理。它们的优先级低于上述缺陷。
