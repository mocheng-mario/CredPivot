### 1. [P1] SSH 自动登录共用明文密码文件，可能把 B 的密码发给 A

位置：[CredPivotPlatform.swift:1215](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner/CredPivotPlatform.swift:1215)、[CredPivotPlatform.swift:1246](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner/CredPivotPlatform.swift:1246)、[ssh-expect-pass.exp:36](/Volumes/WorkSpace/zx/CredPivot/assets/ssh-expect-pass.exp:36)。

所有连接都写 `~/.credpivot/.ssh_expect_password`，外部终端启动与 expect 读取并没有完成握手。A 的终端尚未读取时再启动 B，B 覆盖同一文件；A 随后读取 B 的密码，向 A 服务器认证，并删除 B 也需要的文件。这需要启动时序重叠，不是每次连接必然发生。

此外，写完密码后终端启动报错直接返回，未删除文件；终端没有实际执行 expect 时也没有超时清理。Vault 锁定不能清除此残留。Tabby 等分支还共用 `terminal_launch.sh`，异步启动也会覆盖前一次命令。

最小修复：每次启动使用独立的受限临时资源，创建时就设定权限；失败、取消和超时均清理。对脚本和密码文件一并隔离，不能只给密码文件换名字。不要把启动进程成功当成秘密已经被消费。

### 2. [P1] TOTP 的 `period=0` 可以入库，读取验证码会使 Mac App 退出

位置：[totp.rs:78](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/totp.rs:78)、[totp.rs:112](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/totp.rs:112)、[FFI lib.rs:84](/Volumes/WorkSpace/zx/CredPivot/crates/credpivot-ffi/src/lib.rs:84)。

例如 `otpauth://totp/test?secret=GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ&period=0`：当前依赖的 URI 解析把 period 解析为 u64，构造函数检查 digits 和密钥长度，但没有拒绝 step=0。Core 直接保存该值，生成验证码使用 `new_unchecked`。依赖的 `sign()` 执行 `time / self.step`，进入除零 panic。

Mac 请求经 FFI 的 `Runtime::block_on` 直接执行，没有隔离该 panic；跨越 `extern "C"` 边界会终止进程。这是语言语义支持的结论，未在本机输入执行。[Rust FFI 官方说明](https://doc.rust-lang.org/nomicon/ffi.html#ffi-and-unwinding)。

最小修复：在入库和生成验证码两处验证 period>0、digits/algorithm 范围和真实 Base32 解码；无效输入返回业务错误。FFI 防护可以作为最后一道保护，不能替代参数校验。另一个同类 panic 点是自写 URL 解码对 `%` 后非 ASCII 文本使用字符串字节切片，建议一并去掉该不安全切片。

### 3. [P1] Native Host 新增哈希校验，但校验基准仍与被校验文件同处可写目录

位置：[peer_auth.rs:112](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/peer_auth.rs:112)、[CredPivotPlatform.swift:682](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner/CredPivotPlatform.swift:682)、[ipc.rs:85](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/ipc.rs:85)、[chrome_parent.rs:12](/Volumes/WorkSpace/zx/CredPivot/crates/native-host/src/chrome_parent.rs:12)。

威胁前提是同一用户下的恶意进程可写 `~/.credpivot`，且 Vault 已解锁；不是任意网页远程读取。

1. 对安装副本的校验读取同目录的 `native_host.sha256`。替换 Host 的进程也能替换这个摘要。摘要缺失时，Swift 通常又把 `CREDPIVOT_TRUSTED_NATIVE_HOST` 指向安装副本本身，退化为文件和自己比较。
2. 即使修了文件基准，真实 Host 对父进程仅检查 basename 是否为 Google Chrome。伪装名称的本地程序仍可启动真实 Host，在扩展授权窗口内调用其浏览器接口。
3. Agent 没有限定 Native Host 的命令集合。门槛只列出六类操作；`TotpReveal`、`RecoveryCodesList` 等其他秘密接口没有同等扩展门槛。伪 Host 通过身份校验后可以直接构造这些 Agent 请求。

最小修复：可信摘要/产物身份应由可信 App 提供并固定，不能从对端可同步改写的文件读取；移除“和自身比较”的回退；核实真实浏览器身份，并在 Agent 端限制 Host 命令。当前 ad-hoc 同 App bundle 分支已经收紧，这部分应保留。此建议不要求购买证书，也不宣称能抵御已能任意注入 App 的攻击者。

### 4. [P1] Touch ID 进行中会直接丢弃真实锁屏和睡眠事件

位置：[LifecycleBridge.swift:30](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner/LifecycleBridge.swift:30)。

当前注册的已是系统睡眠、屏幕睡眠和 `screenIsLocked`，不再是容易因 Touch ID 弹窗触发的失焦通知。但三个入口仍共用 `lockAgentUnlessTouchId()`，认证期间直接 return，也没有记录待锁定状态。

用户在指纹确认期间锁屏或合盖，若通知到达时 `isAuthenticating=true`，Vault 不会因该事件锁定；认证结束也不补锁，只能等待其他锁定来源。这个问题有特定时序条件，不表示普通锁屏全部失效。

最小修复：真实锁屏/睡眠必须执行锁定，并使在途认证结果失效。只对确有需要的焦点变化做过滤，不要把真实系统锁定也放入豁免。

### 5. [P1] 恢复改密前的本地恢复点，会把解锁密码退回旧密码

位置：[vault_pipeline.rs:140](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/vault_pipeline.rs:140)、[vault_session.rs:640](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:640)、[credentials_page.dart:1015](/Volumes/WorkSpace/zx/CredPivot/apps/macos/lib/credentials_page.dart:1015)。

步骤是：使用 P1 创建恢复点 → 普通改密为 P2 → 恢复旧点。普通改密不改变 VMK，所以恢复时 MAC 和数据库校验通过；但恢复函数复制的是旧点里的 `vault.json`，连 P1 的包装槽也恢复了。UI 随后锁定并切到目标目录，P2 无法解锁，必须用 P1 或仍有效的恢复密钥。

这与本地恢复点使用当前有效配置的约定冲突：[V1.1 设计:768](/Volumes/WorkSpace/zx/CredPivot/docs/Plans/CredPivot_V1.1_Design.md:768)。这里讨论的是本地恢复点，不是本来就自包含旧密码槽的历史 OVB；也不应描述成数据已经永久丢失。

安全重建后的另一分支也不闭合：旧恢复点现在保留了，但恢复入口始终使用当前新 VMK，无法恢复上一代点，也没有旧凭据输入。

最小修复：区分同一 VMK 代际和重建前代际。同代际恢复数据时保留经过认证的当前配置；跨代际要求明确的旧凭据，不要盲目套当前配置或声称当前密码可用。

### 6. [P1] 自动恢复点创建失败会阻断解锁，失败后还保留已挂载的秘密材料

位置：[vault_session.rs:92](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:92)、[vault_session.rs:209](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:209)、[vault_session.rs:231](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:231)。

`attach_database()` 先把数据库赋给 `self.db`，再载入 SSH signing key，最后用 `?` 执行到期恢复点创建。存在待备份变更且到期时，只要恢复点目录不可写、空间不足或裁剪失败，正确密码解锁也会报失败。重试仍走同一路径。

调用方错误分支只清 `vmk`，没有清 `db` 或 SSH key；因此界面仍显示锁定，但数据库连接及密钥材料没有完整释放。这不是已确认的“锁定接口可读秘密”，而是锁定状态与内存清理不一致。创建 Vault 的相同错误路径还可能在配置已经落盘后不返回恢复密钥。

最小修复：把必要的挂载/认证与可选自动备份分开；备份失败应呈现告警和重试状态，不应阻断可正常打开的库。必要阶段失败时统一清理完整会话；创建成功与恢复密钥交付也须有明确提交点。

### 7. [P1] Chrome service worker 的低层消息接口信任消息自报的 origin

位置：[background.js:116](/Volumes/WorkSpace/zx/CredPivot/apps/chrome-extension/background.js:116)。

`suggest_credentials`、`fill_prepare`、`fill_consume`、`totp_code` 等分支直接接受消息中的 origin、ID、frame/document 信息，且把包含秘密的 Native 响应回给发送者；没有区分可信 popup 与 content script，也没有把 origin 绑定到浏览器提供的 sender 上下文。

前提是 content script 所在渲染进程被攻陷、能以扩展 content script 身份发消息，同时 Vault/扩展门槛已开放。此时可伪造另一站点的 origin，顺着 suggest→prepare→consume 获取该站点秘密。普通网页 JS 并不能直接调用这些扩展内部接口，不把这项写成普通网页即可利用的漏洞。

Chrome 官方明确要求将 content script 消息视为可能由攻击者构造，并限制它能触发的特权操作：[消息安全说明](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#security-considerations)。

最小修复：当前 popup 已有高层填充流程，优先关闭不再需要的低层转发入口；保留的入口根据 sender 身份授权，由 worker 从真实 tab/frame/document 推导上下文，避免把秘密作为任意消息的返回值。

### 8. [P2] 安全重建仍有切换中断窗口，提交后失败也会按旧 VMK 恢复会话

位置：[vault_pipeline.rs:232](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/vault_pipeline.rs:232)、[vault_session.rs:692](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:692)。

两次 rename 之间退出，活动路径不存在，启动没有阶段恢复。旧库通常仍在 backup 目录，不能称为永久丢失。新增的恢复点保留解决了原先无条件删除历史，但它在新库已激活之后才执行且会返回错误；此时 Agent 错误分支仍拿旧 VMK 去挂载已经换钥的新库，挂载再次失败，留下半会话，新恢复密钥也没有返回。

这需要中断或文件操作失败；目前 Flutter 的 `_securityRebuild` 没有按钮接线，因此并非普通用户每次点击都会遇到的现成 GUI 路径，但 Core/Agent 的能力已存在。

最小修复：明确激活提交点，提交后错误按新库状态处理；切换阶段持久化并支持启动恢复；重新挂载失败时完整锁定。保留旧备份直到相关步骤完成，不要用一条通用 Err 分支假设所有失败都未提交。

### 9. [P2] 配置“原子写”没有完成持久化协议，启动恢复函数也未接线

位置：[atomic_config.rs:7](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/atomic_config.rs:7)、[atomic_config.rs:22](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/atomic_config.rs:22)、[atomic_config.rs:47](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/atomic_config.rs:47)。

最小修复：落实目标平台上的文件及目录持久化顺序，并按明确提交状态、解锁及 MAC 校验选择有效配置。不能按存在 .next、时间最新或版本最大就覆盖。这里的风险是断电/系统故障和恢复缺口，不是声称普通 kill 必然损坏文件。

### 10. [P2] App 未实际打包 Host/扩展，开发机缓存掩盖安装依赖；安装回退还会删掉源文件

位置：[make/macos.mk:11](/Volumes/WorkSpace/zx/CredPivot/make/macos.mk:11)、[project.pbxproj:299](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner.xcodeproj/project.pbxproj:299)、[CredPivotPlatform.swift:622](/Volumes/WorkSpace/zx/CredPivot/apps/macos/macos/Runner/CredPivotPlatform.swift:622)、[bootstrap-macos.sh:29](/Volumes/WorkSpace/zx/CredPivot/scripts/bootstrap-macos.sh:29)。

### 12. [P2] 服务器选择 SSH key 改的是全局身份，连接之间会互相干扰

位置：[vault_session.rs:193](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/vault_session.rs:193)、[server_login_page.dart:321](/Volumes/WorkSpace/zx/CredPivot/apps/macos/lib/server_login_page.dart:321)、[ssh_agent.rs:116](/Volumes/WorkSpace/zx/CredPivot/crates/agent/src/ssh_agent.rs:116)。

关联 key 已经接线，但实现是覆盖唯一 `ssh_signing_key`。A 连接选 key A 后、签名完成前，B 选择 key B，Agent 会拒绝 A 公钥的签名请求；后续不指定关联 key 的连接也继续受 B 的选择影响。这不影响已经认证完成的 SSH 会话。

普通启动命令也没有显式绑定 CredPivot IdentityAgent，需要用户另有 SSH 配置才能使用它。密码 expect 分支虽然禁用公钥认证，却仍调用选择 key，无谓改变其他连接的全局状态。

最小修复：不要通过改全局默认身份承诺每连接 key 选择；短期可以明确限制/停用这种选择能力。要支持多 key，应按请求公钥稳定查找对应身份，并由连接配置约束目标 key；密码认证分支不要修改 SSH Agent 身份。

### 13. [P2] TOTP URI 解析失败仍静默改为 SHA1/6/30，短密钥的非默认参数会丢失

位置：[totp.rs:81](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/totp.rs:81)。

UI 和导出已经贯通完整参数，原先那条问题已修复。但 URI 解析失败仍提取 secret 并强制默认参数。例如 `otpauth://totp/test?secret=JBSWY3DPEHPK3PXP&algorithm=SHA256&digits=8&period=60`，80-bit secret 被依赖的严格构造拒绝后，Core 回退为 SHA1/6/30，而不是保留 URI 参数。其他算法/位数错误也会被掩盖。

最小修复：如果要兼容短密钥，就独立保留并校验 URI 的算法、位数和周期；不支持的参数明确报错。只允许纯 secret 输入采用默认值，不要把解析失败解释为用户同意默认值。

### 14. [P2] expect 会修改密码首尾空白，合法密码无法认证

位置：[ssh-expect-pass.exp:48](/Volumes/WorkSpace/zx/CredPivot/assets/ssh-expect-pass.exp:48)，Runner 副本相同。

Swift 写入的是完整密码，没有追加行尾；脚本读取后却统一 trim 空格、制表和换行。密码 ` pass ` 会变成 `pass`，并按重试逻辑反复发送错误值。

最小修复：密码文件按原内容消费，不对秘密做 trim。若兼容其他输入源需去掉协议换行，应只在该输入源处理明确的分隔符。

### 15. [P2] 首次创建后的恢复密钥复制绕过已有敏感剪贴板通路

位置：[main.dart:243](/Volumes/WorkSpace/zx/CredPivot/apps/macos/lib/main.dart:243)。

普通密码、网站恢复码已经调用 `copyConcealed`，但 Vault 恢复密钥使用 `Clipboard.setData`，没有同样的隐藏标记和到期清除。复制后普通剪贴板仍保留该主恢复材料；锁定并不会补上这次复制的清理。

最小修复：复用已有敏感复制方法并遵守锁定状态。隐藏标记不是防恶意剪贴板读取的强隔离，不应据此宣称绝对安全，但至少要保持产品自己的秘密处理约定一致。

### 16. [P2] 登录项编辑后保留旧 selection，连续编辑会产生伪冲突

位置：[credentials_page.dart:129](/Volumes/WorkSpace/zx/CredPivot/apps/macos/lib/credentials_page.dart:129)、[credentials_page.dart:240](/Volumes/WorkSpace/zx/CredPivot/apps/macos/lib/credentials_page.dart:240)。

第一次编辑后 `_refresh` 替换 `_items`，没有按 ID 更新 `_selected`。不重新点选条目直接再次编辑，传入的是旧字段和旧 `current_revision`，正常单用户操作会收到 revision conflict。服务端冲突检查本身是正确的，不应该为了消除报错而绕过它。

最小修复：刷新后按 selected ID 重新绑定最新记录，不存在则清空；服务器页已有相同处理，可直接沿用局部逻辑。

### 17. [P2] 浏览器填登录与填 MFA 会自动选中不同账号

位置：[fill_flow.js:52](/Volumes/WorkSpace/zx/CredPivot/apps/chrome-extension/fill_flow.js:52)、[fill_flow.js:66](/Volumes/WorkSpace/zx/CredPivot/apps/chrome-extension/fill_flow.js:66)。

登录填候选第一项 A；MFA 则重新查询并选第一项有关联 TOTP 的 B。一个站点有多账号且 A 没有关联 TOTP、B 有时，先点登录再点 MFA 会填 A 的账号密码和 B 的验证码。两次操作没有共同的账号选择约束。

最小修复：显式选择账号，并使同一填充流程的 MFA 使用该账号；没有关联就提示，不要自动跳到另一个账号。若记忆上次选择，需同时处理导航、锁定和过期，不要做长期全局缓存。

### 18. [P2] 业务提交和备份 dirty 标记不在同一事务，成功写入可能报错或漏进自动备份

位置：[vault_db.rs:49](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/vault_db.rs:49)、[vault_db.rs:107](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/vault_db.rs:107)、[repo_m2.rs:153](/Volumes/WorkSpace/zx/CredPivot/crates/core/src/repo_m2.rs:153)。

Repository 已有业务事务，不是“所有写入都没有事务”。问题是它提交后才回到 VaultDatabase 单独调用 `mark_restore_dirty`。第二步失败时，API 返回失败但业务已经成功；两步之间退出且原 dirty=0 时，新数据已经写入，却不会触发后续自动恢复点，直至另一写操作再置 dirty。

最小修复：把 dirty 标记放入已有业务事务的提交之前。应调整现有提交边界，不需要新增通用事务框架；也不要只吞掉 dirty 写失败来掩盖备份状态丢失。

## 交付缺口与可选改进

这些与上面运行逻辑缺陷分开，不把尚未接线的功能写成已经执行失败的案例。

1. **Chrome 保存入口未完成。** worker/Host 有保存命令，但 popup 和 content script 没有可达的保存 UI/采集入口。当前个人版验收明确包含一条站点的保存/填充；不能仅凭后台存在分支认为保存已完成。
2. **安全中心有未接线的方法。** `_securityRebuild`、`_verifyOvb`、`_verifyRecoveryKey` 没有对应按钮调用，界面仍展示相关输入/状态。先决定哪些能力属于本轮个人版，再补入口或去掉误导性占位；不要把“写了方法”算作用户功能已完成。
3. **origin 仍使用手写切分。** `https://example.com:443`、域名大小写、无路径但有 fragment 等与 Chrome `new URL(...).origin` 不一致，会导致导入后匹配不到。建议采用标准 URL 解析与统一 origin 序列化，保留此次已修好的非默认端口语义。
4. **未知新 Schema 没有拒绝写入。** `user_version > 8` 时各迁移直接跳过，旧程序仍继续打开；属于未来升级/降级风险。建议增加简单的版本上限拒绝或明确只读策略，无需建设兼容框架。
5. **暂不建议拆更多架构层。** Core/Agent/UI 的总体分工足够；优先去掉跨层默认值不一致、全局可变连接状态，以及提交后仍返回普通失败的路径。重复展示代码或文件偏大不是本轮首要问题。

## 测试源码观察及建议顺序

生产代码阅读完成后，静态检查了 Rust 集成测试、相关内联测试、Flutter widget 测试和 RunnerTests，没有执行。

现有用例能覆盖基础创建/解锁、改密保持 VMK、普通 CRUD 冲突、OVB 往返/篡改、基本恢复和迁移补列。`password_change_crash` 是直接调用恢复 helper 的模拟，不是实际启动恢复；`m3_fault` 主要检查非空目标拒绝，不能证明磁盘满或激活中断可恢复。TOTP 基础用例没有覆盖零周期、短密钥加非默认参数的组合。Flutter 为基础启动烟测，Swift 测试仍是模板。

建议后续修复和定向验收按以下顺序，不代表本轮已创建或执行测试：

1. 先修秘密泄漏/崩溃和身份边界：两次 SSH 启动交错、启动失败清理、零周期 TOTP、伪 Host/伪 sender、认证期间锁屏。

3. 校验个人版安装产物：干净用户 HOME、仅拷贝 App、来源路径消失后更新扩展 ID。不要用开发机已有缓存当成功证据。
4. 最后验证常见数据规模和连续操作：超过 200 条登录的服务器关联、连续编辑两次、同站点多账号 MFA、连续 SSH 多 key。

本轮没有发现需要为解决这些问题而引入新架构层、事件总线或通用工作流框架的理由。
